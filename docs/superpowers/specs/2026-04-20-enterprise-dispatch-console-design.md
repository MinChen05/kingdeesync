# Kingdee 企业级调度工作台重设计

## 1. 背景

当前仓库已经具备可运行的金蝶数据同步桌面程序，但现有产品形态仍更接近“可用工具”而不是“企业级调度工作台”：

- 业务核心已经明确，围绕金蝶同步、调度、历史和配置管理展开。
- 当前 GUI 已有 Win11 风格外壳和多页面结构，但管理者视角不足，首页价值不够集中。
- 现有界面更偏功能承载，尚未形成统一的运行语义、风险表达和处置闭环。
- 目标用户不是一线开发或纯值守工程师，而是企业内部 IT 管理者。

本次设计不是做一个泛化的后台皮肤，而是把现有金蝶同步产品重定义为一套面向企业内部 IT 管理者的企业级桌面调度工作台。

## 2. 设计结论

### 2.1 最终定位

产品定位为：

`一套面向企业内部 IT 管理者的企业级调度工作台`

核心使用方式为：

- 默认先看全局监控总览。
- 发现异常后进入异常处置。
- 再进入历史追踪完成复盘和审计。
- 最后通过系统配置做长期治理。

### 2.2 选型结论

本次重设计采用：

- 视觉方向：`冷静控制室`
- 交互方向：`吸收夜间指挥舱的异常处置效率`
- 产品语义方向：`以 Run、状态模型、异常分类、恢复动作构成统一语言`

不采用纯深色值守台作为主视觉，因为它更偏运维值守，不够匹配企业内部 IT 管理者的长期使用场景。

不采用纯审计驾驶舱作为主视觉，因为它会削弱调度与异常处理的即时操作感。

## 3. 用户与场景

### 3.1 主要用户

主要用户为企业内部 IT 管理者，关注：

- 系统整体是否健康
- 哪些同步任务正在异常
- 异常影响范围和业务风险
- 是否需要人工介入
- 故障是否形成闭环

### 3.2 主要场景

产品需要同时覆盖以下两个主场景，并以监控总览优先：

1. 日常监控
   - 查看同步健康度、延迟、失败趋势和风险分布。
2. 异常处置
   - 快速定位失败任务、判断影响、发起恢复动作并追踪责任闭环。

默认首页采用“双模式并重，但先监控后处置”的结构。

## 4. 目标与非目标

### 4.1 目标

- 让用户在 10 秒内理解当前系统整体状态。
- 让首页成为问题发现入口，而不是功能堆叠页。
- 用统一状态模型解释同步运行、失败、恢复和责任。
- 让异常处理动作可直达、可追踪、可审计。
- 让产品整体呈现出高信任感、企业感和桌面控制台气质。

### 4.2 非目标

- 不在本次设计中扩展全新业务域。
- 不把产品改成面向开发者的工程调试工具。
- 不做深色值守风格的大屏化设计。
- 不将配置页做成参数无边界堆积的实施工具页。

## 5. 设计原则

产品遵循以下设计原则：

1. `总览先于明细`
   - 首页先给出结论、风险和入口，再展开细节。
2. `风险先于日志`
   - 用户先看到影响范围、严重等级和建议动作，而不是技术日志。
3. `动作贴着问题放`
   - 异常旁边直接提供重试、续跑、转派等操作。
4. `状态语义全局一致`
   - 同一 Run 在不同页面使用同一状态定义和同一颜色语义。
5. `桌面优先而非网页搬运`
   - 强化 Windows 桌面控制台的稳定感、空间组织和长时间使用舒适度。

## 6. 视觉方向

### 6.1 整体气质

整体采用“冷静控制室”方向：

- 以浅色高阶企业风为主。
- 用蓝白主色和钢感边界传递专业、可信、稳定。
- 保留少量高对比状态色表达预警和严重风险。
- 整体不追求炫技，而强调长期使用的阅读效率和决策信任感。

### 6.2 色彩策略

建议采用如下语义色：

- 基础背景：瓷白、雾白、浅钢蓝
- 主强调色：天空蓝到稳重蓝
- 信息色：蓝色
- 成功色：绿色
- 预警色：琥珀色
- 危险色：红色
- 禁用/未知：灰色

所有颜色必须服务于状态语义，避免同一状态在不同页面使用不同颜色。

### 6.3 字体与密度

- 标题与数据重点使用 Windows 原生友好的现代字体组合。
- 中文正文优先保证清晰、稳定和屏幕阅读舒适度。
- 数据面板允许中高信息密度，但必须保持明显层级。
- 不使用夸张装饰字体，不牺牲企业软件的专业感。

### 6.4 动效策略

- 只在高价值区域使用克制动效，如页面进入、状态刷新、告警提醒。
- 高风险状态可用轻量脉冲或呼吸感提示。
- 不使用花哨、分散注意力的动画。

## 7. 信息架构

### 7.1 一级导航

产品采用 `左侧纵向导航 + 顶部指挥栏 + 中央主画布` 的桌面结构。

一级导航包括：

- `总览`
- `调度中心`
- `异常处置`
- `任务历史`
- `系统配置`

辅助入口包括：

- `通知中心`
- `账户 / 权限`
- `系统状态`

### 7.2 顶部指挥栏

顶部不只是搜索条，而是指挥栏，承载：

- 当前组织与环境标签
- 当前时间和全局值守状态
- 全局搜索
- 关键动作入口

关键动作固定为：

- `新建调度`
- `批量重试`
- `导出日报`

## 8. 首页设计

### 8.1 首页职责

首页负责回答四个问题：

1. 现在系统整体是否健康
2. 哪些任务正在异常或有风险
3. 这些异常是否影响业务
4. 我下一步最该点哪里

### 8.2 主屏结构

首页采用三段式主画布。

#### 第一层：全局态势

顶部总览区包括：

- 今日同步健康分
- 当前状态总结
- 成功率
- 失败任务数
- 延迟任务数
- 影响业务单据量

这一层以结论和风险概览为主，不展示技术细节。

#### 第二层：异常与调度核心区

这一层是首页主战场，采用左右双栏：

- 左侧：`异常处置面板`
  - 展示当前最重要的 5 到 8 条异常
  - 展示任务名、失败阶段、影响范围、最近重试时间、负责人
  - 直接提供 `查看原因`、`立即重试`、`转派处理`
- 右侧：`调度运行矩阵`
  - 展示运行中、等待中、延迟、阻塞的任务分布
  - 帮助用户理解拥塞点和阻塞区域

#### 第三层：趋势与治理

底部区域偏管理视角，包括：

- 7 天成功率/延迟趋势
- 失败原因分布
- 处置闭环看板

这一层用于支持复盘、治理和中短期管理决策。

## 9. 核心页面设计

### 9.1 调度中心

调度中心负责解释任务是否按计划流动。

页面结构：

- 左侧：任务筛选区
- 中间：任务运行矩阵 + 时间轴
- 右侧：任务详情抽屉

高频动作：

- `立即执行`
- `暂停调度`
- `恢复调度`
- `调整优先级`
- `查看依赖影响`

### 9.2 异常处置

异常处置页负责事件指挥与恢复闭环，不是单纯日志列表。

页面结构：

- 顶部：高风险异常数、影响业务量、超时未处理数
- 中间：按严重度和影响范围排序的异常事件列表
- 右侧：异常处置抽屉

高频动作：

- `立即重试`
- `断点续跑`
- `重新生成批次`
- `转派责任人`
- `标记已知问题`
- `生成事件报告`

### 9.3 任务历史

任务历史页负责追踪、审计和复盘。

页面能力：

- 按任务名、批次号、错误码、责任人、时间区间检索
- 展示失败率变化、重复故障任务、平均恢复时间
- 支持查看完整批次轨迹和状态流转

### 9.4 系统配置

系统配置页应表现为“安全配置中台”，而不是参数堆场。

分区包括：

- `连接管理`
- `表单与映射`
- `调度策略`
- `通知与权限`

默认只展示常用配置，高风险项归入高级设置。

## 10. 关键组件

### 10.1 指挥摘要条

出现在首页和调度中心顶部，展示：

- 当前值守状态
- 环境标签
- 健康分
- 告警数量
- 最近失败时间

### 10.2 指标卡组

用于展示关键指标，并且必须支持点击下钻。

视觉分级：

- 正常：冷静浅色
- 预警：琥珀边框
- 严重：红色高亮并带轻量提醒

### 10.3 任务运行矩阵

这是调度中心的核心组件。

- 横轴：时间或批次
- 纵轴：任务分组
- 单元格状态：运行中 / 等待 / 延迟 / 失败 / 已完成 / 已阻塞

### 10.4 异常事件列表

异常列表以事件卡片而非普通表格呈现，至少展示：

- 任务名称
- 错误阶段
- 严重等级
- 影响范围
- 最近处理动作
- 责任人
- 主操作按钮

排序优先级为：

1. 严重度
2. 影响范围
3. 持续时间

### 10.5 右侧详情抽屉

详情查看优先采用右侧抽屉，不频繁开新窗口。

抽屉包含：

- 批次摘要
- 错误链路
- 最近成功记录
- 建议动作
- 可执行操作

### 10.6 时间线与批次轨迹

在历史页和异常详情中使用纵向时间线展示：

- 启动
- 分页抓取
- 写入数据库
- 重试
- 结束或中断

### 10.7 全局通知中心

通知中心只承接高价值通知：

- 高风险异常
- 调度策略变更
- 人工处置闭环结果

普通成功日志不进入通知中心。

## 11. 交互规则

### 11.1 动作规则

- 动作必须靠近问题出现位置。
- 列表页中就能发起核心恢复动作。
- 高风险动作必须二次确认，并明确影响范围。
- 低风险动作尽量无打断完成。

### 11.2 信息展开规则

- 首页与列表页优先显示结论、影响和动作建议。
- 技术细节只在详情抽屉和历史页展开。
- 弹窗仅用于确认和阻断性错误，不用于普通查看。

### 11.3 跳转规则

- 首页下钻进入列表页时，必须带上上下文筛选条件。
- 从异常到历史、从历史到详情的跳转必须保留任务上下文。

### 11.4 键盘效率

桌面程序应优先支持高价值快捷操作，例如：

- `Ctrl+K` 全局搜索
- `F5` 刷新当前视图
- `Alt+1-5` 一级导航切换
- `Ctrl+R` 对当前任务发起恢复动作

## 12. 运行状态模型

### 12.1 Run 作为统一对象

每一次同步任务统一抽象为一个 `Run`，并拥有唯一编号。

### 12.2 状态定义

Run 只能处于以下状态之一：

- `待执行`
- `执行中`
- `部分成功`
- `成功`
- `失败`
- `已阻塞`
- `恢复中`
- `已暂停`

这些状态必须贯穿首页、调度中心、异常处置、任务历史和通知中心。

### 12.3 部分成功

`部分成功` 是独立状态，不可归入成功或失败。

界面中必须明确展示：

- 成功部分占比
- 失败对象范围
- 是否影响核心业务
- 是否允许继续补偿

在总览中，部分成功应归入中风险。

### 12.4 陈旧运行

如果任务长时间无心跳更新但未正常结束，应标记为 `陈旧运行 stale run`。

陈旧运行不能被静默归为失败，而要提供明确提示与处理入口。

## 13. 异常分类与恢复语义

### 13.1 异常分类

所有错误统一归入以下四类：

- `配置异常`
- `环境异常`
- `集成异常`
- `写入异常`

默认展示给用户的不是原始堆栈，而是：

- 异常类别
- 影响范围
- 是否可自动恢复
- 建议动作

### 13.2 恢复动作

恢复动作明确分为三类，不能全部叫“重试”：

1. `重新重试`
   - 适用于瞬时失败
2. `断点续跑`
   - 适用于长链路中断后的继续执行
3. `重新生成批次`
   - 适用于配置变化或原批次结果不再可信

界面必须明确说明这些动作的差异，尤其是是否可能重复写入。

### 13.3 责任闭环

每个异常事件都应追踪：

- 发现时间
- 责任人
- 当前处置动作
- 最后更新时间
- 关闭原因

## 14. 桌面端约束

### 14.1 窗口与布局

- 默认面向 1366px 及以上桌面环境优化。
- 主布局优先保证 1280px 宽度下的稳定使用。
- 较窄窗口下允许侧栏收缩、右侧详情抽屉覆盖，但不打散主工作流。

### 14.2 桌面感要求

- 强化固定导航、指挥栏、抽屉、状态栏等桌面控制台元素。
- 避免完全照搬网页后台常见的松散卡片布局。
- 适配长时间值守和多窗口协作使用。

## 15. 验收标准

### 15.1 体验验收

- 用户进入首页后，应在 10 秒内看懂整体健康度、异常数量、影响范围和下一步入口。
- 从首页发现问题到进入异常详情并发起处理动作，应控制在 3 次点击以内。
- 首页不得被日志、参数或长表格淹没。

### 15.2 功能验收

- 首页关键指标全部支持下钻。
- 调度中心支持执行、暂停/恢复、优先级调整和依赖查看。
- 异常处置支持查看原因、重试、续跑、重新生成批次、转派与关闭。
- 任务历史支持完整 Run 审计链路查看。

### 15.3 状态验收

- 同一个 Run 在所有页面状态表达一致。
- 部分成功单独展示、单独统计、单独告警。
- 陈旧运行可识别且可处理。
- 三类恢复动作语义可区分。

### 15.4 视觉与交互验收

- 产品整体符合“冷静控制室”的视觉方向。
- 所有高风险动作都有明确确认文案。
- 详情查看以抽屉为主，连续操作不中断。

## 16. 实施边界

本设计文档定义的是产品重设计方案，不等同于实现计划。

后续实现计划需要在本设计的基础上进一步拆分：

- 视觉与设计 token 更新
- 主框架重构
- 首页重做
- 页面级组件替换
- 运行状态与恢复语义落地
- 验收与测试补齐

## 17. 最终结论

本次重设计要完成的，不是简单的界面换皮，而是四个层面的升级：

1. 从功能堆叠升级为管理者工作流
2. 从日志导向升级为风险与处置导向
3. 从零散状态升级为统一运行语义
4. 从工程工具升级为可交付的企业级桌面产品

最终产品应呈现为：

`视觉上冷静、交互上高效、语义上统一、管理上可信的企业级调度工作台`
