# Kingdee 企业级发布改造设计

## 1. 背景

当前仓库已经具备可运行的产品雏形：

- Python 仍是当前交付主线。
- SQL Server 是默认数据库口径。
- GUI、CLI、配置访问器、同步编排、运行记录和部分恢复机制已经存在。
- `.NET` 迁移线已经建立，但定位仍是迁移与 parity，对当前发布不构成主线替代。

从“可运行工具”到“企业级可发布产品”的主要差距，不在单个功能，而在发布工程、运行稳定性、运维能力、安全口径和长期可维护性。

当前代码库的几个关键信号如下：

- 质量门禁尚未稳定为绿灯，发布基线不可靠。
- 核心同步链路和数据库管理仍然存在过重文件与职责耦合。
- 测试保护偏向 GUI 外壳，核心同步与数据写入边界的自动化保护不足。
- 仓库卫生、安装升级、诊断工具、迁移脚本与交付文档仍未达到企业交付要求。

本设计的目标，是定义一条以 Python 主线为基线的发布改造路线，使本项目达到可试点交付并最终正式发布的水准。

## 2. 设计范围

本设计覆盖以下内容：

- 发布基线与支持矩阵
- 质量门禁与测试体系
- 核心架构收口与职责拆分
- 数据一致性、异常恢复和运行记录
- 安装、升级、迁移与诊断能力
- 安全、日志、审计与运维文档

本设计不覆盖以下内容：

- 将 `.NET` 版本提升为本次 GA 主线
- 大规模重写现有 GUI
- 与当前发布目标无关的全量重构
- 新业务表单的大范围新增

## 3. 发布假设

本次发布默认基于以下假设：

- 目标部署环境为 Windows 桌面或内网运维终端。
- Python 版本仍是当前 GA 主线。
- SQL Server 为默认生产数据库口径，MySQL 保留兼容路径但不作为主要验收基线。
- `.NET` 迁移工程继续保留，但不作为本次正式发布的阻塞项。
- 产品需要支持手动同步、定时同步、连接测试、历史查询、日志查看和异常恢复。

如果后续业务目标改变，例如要求 `.NET` 直接替代 Python 主线，或要求支持大规模无人值守服务化部署，则需要额外拆分新 spec。

## 4. 目标与发布标准

### 4.1 总体目标

将当前项目从“研发可运行版本”提升为“企业可验收、可部署、可运维、可升级、可回滚”的正式发布版本。

### 4.2 正式发布最低标准

正式发布前，必须同时满足以下标准：

1. 质量门禁稳定通过。
2. 安装包可重复构建，安装与升级路径明确。
3. 运行过程具备可追踪的 `run_id`、状态记录、日志和诊断能力。
4. 同步失败后具备明确的恢复语义，不会静默丢数或产生不可见的重复执行。
5. 配置、凭据、日志与数据库权限满足基本安全要求。
6. 交付文档完整，包含部署、升级、回滚、诊断和故障处理说明。

## 5. 方案选型结论

本项目采用“发布收口型”方案：

- 以 Python 主线为发布基线。
- 以 P0、P1、P2 三阶段推进。
- 先收口发布质量，再推进深层重构和扩展交付能力。
- `.NET` 继续做迁移与 parity，不与本次 GA 目标绑定。

不采用“大规模重构优先”方案，因为其周期长、风险高，且会把发布问题拖成长期架构项目。

不采用“.NET 主线切换优先”方案，因为当前文档和代码口径均以 Python 为主线，直接切换会同时叠加迁移风险与发布风险。

## 6. 目标架构

### 6.1 目标分层

发布版应收敛为以下五个清晰单元：

1. `Presentation`
   - GUI 页面、CLI 入口、用户反馈和显示逻辑。
   - 不直接承载同步流程编排、数据库写入细节和恢复规则。

2. `Application Services`
   - 对外暴露同步、连接测试、配置保存、历史查询和恢复操作。
   - 负责协调 UI/CLI 与核心同步引擎之间的边界。

3. `Sync Core`
   - 负责同步任务编排、单表执行、重试、断点、状态流转、心跳与取消语义。
   - 输出结构化结果对象，而不是松散字典协议。

4. `Persistence & Integration`
   - 负责数据库 provider、writer、upsert、运行记录、审计日志与外部接口客户端。
   - Schema 变更通过显式 migration 管理，而不是运行时隐式补齐。

5. `Release & Operations`
   - 负责安装包、版本号、升级、回滚、诊断工具、支持矩阵和交付文档。

### 6.2 边界约束

发布改造必须遵循以下边界：

- GUI 不能再直接依赖核心单例和隐式全局状态。
- 同步结果必须具备结构化模型，至少统一成功、部分成功、失败、异常终止四类状态。
- 数据库 schema 检查与 schema 修改不能继续隐式混入核心业务写流程。
- 运行记录、错误分类、日志输出与 UI 呈现必须共享同一套状态语义。

## 7. 核心数据流设计

发布版的数据流统一定义如下：

`GUI/CLI -> Application Service -> Run Coordinator -> Form Executor -> API Client -> Writer/Upsert -> Run Repository/Audit Log`

其中：

- `Run Coordinator` 负责任务初始化、状态推进、心跳、结束汇总和异常恢复。
- `Form Executor` 负责单表的过滤、分页、写入和表级错误收敛。
- `Run Repository` 负责任务级持久化。
- `Audit Log` 负责审计与运维追踪。

每次同步必须具备：

- 唯一 `run_id`
- 明确开始时间、结束时间、心跳时间
- 统一状态值
- 结构化结果明细
- 可追踪的失败原因

## 8. 错误处理与恢复设计

### 8.1 错误分类

所有同步错误统一归入以下四类：

1. `configuration_error`
   - 配置缺失、配置不合法、驱动缺失、环境变量错误。

2. `environment_error`
   - 数据库不可达、ODBC 驱动缺失、文件权限不足、磁盘写失败。

3. `integration_error`
   - 金蝶接口超时、认证失败、接口返回异常、分页中断。

4. `write_error`
   - 表结构不匹配、批量写入失败、主键冲突、数据转换错误。

### 8.2 恢复原则

正式发布版必须满足以下恢复原则：

- 异常退出后的运行任务可以被识别为 stale run。
- stale run 的状态修复必须可追踪、可审计、可区分于正常失败。
- 断点恢复只能在定义清晰且已验证的场景下启用，不能造成重复插入或隐藏数据不一致。
- 完全同步与增量同步必须有不同的恢复语义，不能混用。

## 9. 测试与质量设计

### 9.1 质量门禁

发布版质量门禁至少包括：

- `ruff`
- `mypy`
- 单元测试
- 关键集成测试
- 安装后烟雾测试

质量门禁必须由 CI 托管，任何发布包都必须从绿灯提交构建。

### 9.2 测试金字塔

测试结构调整为：

1. `Unit Tests`
   - 配置解析
   - 状态转换
   - 错误分类
   - 结果模型
   - 恢复规则

2. `Integration Tests`
   - `DataSyncManager` 编排
   - `FormSyncRunner` 重试与断点
   - `SyncRunRepository` 状态持久化
   - `kingdee_api` 异常契约
   - SQL Server 写入与 migration

3. `UI Smoke Tests`
   - 保留当前 Win11 页面骨架回归，但不再作为测试主体。

4. `Packaging Smoke Tests`
   - 安装、启动、连接检查、日志目录生成、版本显示。

### 9.3 发布前必须补齐的自动化覆盖

以下自动化测试在正式发布前必须存在：

- 同步任务成功完成
- 同步任务部分成功
- 同步任务异常退出后恢复
- 配置错误快速失败
- 金蝶接口超时重试
- SQL Server 写入失败后的错误归档
- 运行记录开始、心跳、结束、异常恢复全链路

## 10. 发布工程设计

### 10.1 安装与构建

发布版必须提供可重复构建的安装物，并至少支持以下能力：

- 版本号可见
- 构建产物可追溯到 git 提交
- 启动前依赖检查
- 驱动与配置缺失提示
- 默认日志目录与诊断目录

### 10.2 升级与回滚

发布版必须具备：

- 明确的版本升级说明
- 配置兼容策略
- 数据库 migration 顺序
- 升级失败的回滚说明
- 禁止跨大版本无说明覆盖安装

### 10.3 诊断工具

发布版必须新增 `doctor` 或等价诊断能力，至少输出：

- 应用版本
- Python 版本
- ODBC 驱动信息
- 数据库连接检查结果
- 金蝶接口连接检查结果
- 当前配置摘要（脱敏）
- 最近一次运行状态
- 最近错误日志路径

## 11. 安全设计

正式发布版最低安全要求如下：

- 配置中的凭据必须支持加密存储或等价保护。
- UI、日志和诊断导出中不得输出明文敏感信息。
- 默认使用最小权限数据库账号。
- 生产、测试、本地环境必须可区分，禁止默认共用真实连接配置。
- 审计日志需要保留关键操作轨迹，包括开始同步、结束同步、异常恢复与配置变更。

## 12. 文档与运维设计

交付包必须配套以下文档：

- 部署手册
- 升级手册
- 回滚手册
- 运维巡检手册
- 故障诊断手册
- 支持矩阵
- FAQ 与错误码说明

文档不再以开发 README 替代正式交付文档。

## 13. 分阶段实施设计

### 13.1 P0：发布收口

目标：建立可信发布基线。

范围：

- 修复当前 lint 与测试红灯。
- 清理重复定义、明显职责冲突和仓库卫生问题。
- 固化质量门禁并接入 CI。
- 冻结支持矩阵。
- 明确单实例、心跳和 stale run 恢复语义。
- 收敛配置与日志脱敏规则。

P0 完成标准：

- `main.py check` 对应门禁稳定通过。
- 核心同步链的关键路径有自动化测试保护。
- 运行失败可以稳定记录并可恢复。
- 仓库可作为发布基线使用。

### 13.2 P1：试点交付

目标：具备小范围企业试点能力。

范围：

- 拆分过重文件，重点治理同步编排与数据库管理边界。
- 引入结构化结果模型和统一错误分类。
- 建立显式 migration。
- 提供安装包、升级说明与诊断工具。
- 补齐集成测试。

P1 完成标准：

- 可在试点环境安装、运行、升级。
- 关键故障可通过诊断工具与文档定位。
- 同步结果与失败原因可被运维人员解释和追踪。

### 13.3 P2：正式发布

目标：达到可规模交付水准。

范围：

- 建立正式版本化发布流程。
- 补齐性能基线、容量说明和监控告警建议。
- 完成部署、升级、回滚与运维文档体系。
- 对 `.NET` parity 输出明确口径，但不改变 Python 主线定位。

P2 完成标准：

- 发布流程可重复执行。
- 交付物完整。
- 发布后问题可通过日志、运行记录、诊断工具和文档闭环处理。

## 14. 风险与控制

### 14.1 主要风险

- 在发布收口阶段引入过度重构，导致交付周期失控。
- 在主线未稳定前同步推进 `.NET` 主线切换，导致双线风险叠加。
- 核心状态语义未统一，继续造成 UI、日志、仓储与恢复逻辑互相偏离。
- 自动化测试覆盖不足，导致回归只能依赖人工验证。

### 14.2 控制措施

- 严格按 P0、P1、P2 分期推进，不在 P0 引入与发布无关的大规模重写。
- 所有发布前改造先落测试与门禁，再落实现细节。
- 将“统一状态模型、错误分类、运行记录语义”作为优先级最高的结构性治理项。
- `.NET` 仅保留 parity 与迁移验证，不改变当前 GA 口径。

## 15. 最终结论

本项目达到企业级发布水准的正确路径，不是立即重写或立即切主线，而是：

1. 以 Python 主线为基础收口发布质量。
2. 用 P0 建立可信发布基线。
3. 用 P1 补齐安装、升级、诊断和结构化运行能力。
4. 用 P2 完成交付工程和正式发布流程。

后续 implementation plan 不应直接覆盖全部范围，而应先从 `P0：发布收口` 开始，单独形成可执行计划。
