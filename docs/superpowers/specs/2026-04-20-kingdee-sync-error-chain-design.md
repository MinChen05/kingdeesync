# 金蝶同步故障链修复设计

- 日期: 2026-04-20
- 范围: `PRD_INSTOCK` 写库校验、金蝶会话异常识别、应用退出/调度竞态
- 状态: 已确认设计，待用户审阅

## 1. 背景

本次排障基于 Windows 服务器运行日志，暴露出一条连续的故障链：

1. 金蝶接口在分页查询过程中返回会话失效类错误对象。
2. 查询层未严格识别异常响应，部分错误对象被当成业务数据继续下游处理。
3. `prd_instock` 写库前未校验 `FBILLNO` 必填约束，坏记录进入 SQL Server staging 和普通批量写入流程。
4. 单条坏记录触发 `FBILLNO` 非空约束，最终导致整批 `PRD_INSTOCK` 写入失败。
5. 应用退出后，后台同步流程仍在尝试创建并发任务和向已销毁的 Qt 对象发信号，额外产生生命周期异常。

本设计目标是修复整条故障链，而不是仅屏蔽单点报错。

## 2. 问题陈述

### 2.1 查询入口误判

当前分页响应解析过于宽松。对于部分异常返回结构，系统没有在入口处直接判定失败，而是继续参与页数据映射、计数和回调，导致“会话信息已丢失，请重新登录”之类的错误对象可能被视作正常记录。

### 2.2 `prd_instock` 数据校验缺口

`_prepare_prd_instock_data()` 当前对主键和必填字段的校验不够严格：

- 使用 `or 0` 掩盖空主键，降低了无效记录识别能力。
- 未对 `FBILLNO` 进行业务层必填校验。
- staging 和普通批量写入前缺少针对 `prd_instock` 的二次兜底过滤。

结果是单条坏记录可以拖垮整批写入。

### 2.3 生命周期与退出竞态

应用退出时，调度器、同步执行器和 GUI 日志桥之间缺少统一的 shutdown 协调：

- 退出流程开始后仍可能继续调度新任务。
- `ThreadPoolExecutor` 可能在解释器退出阶段仍尝试提交任务。
- GUI 日志 handler 仍向已销毁的 Qt signal emitter 发信号。

这会在真实故障之后追加不必要的二次异常，污染日志并增加排障成本。

## 3. 设计目标

本次设计目标如下：

1. 会话失效或异常响应不得再伪装成业务数据进入下游。
2. `prd_instock` 的坏记录必须在应用层被识别并剔除，不能再依赖数据库约束兜底。
3. 单条或少量坏记录不应导致整批 `PRD_INSTOCK` 写入归零。
4. 应用退出后不得再提交新的同步任务，也不得再向已销毁的 GUI 对象发信号。
5. 同步统计和日志口径需要区分查询异常、无效数据、去重与真正写库失败。

## 4. 非目标

本次不做以下内容：

1. 不重构整个同步架构。
2. 不调整其他业务表的字段映射规则，除非复用本次新增的通用防御能力。
3. 不引入新的任务编排框架或 Qt 生命周期管理框架。
4. 不改变现有同步模式定义（增量、全量、完全同步）。

## 5. 方案比较

### 方案 A: 最小止血

只在 `prd_instock` 写库前补 `FBILLNO` 校验，并在退出阶段增加简单守卫。

优点：

- 变更最小。
- 可快速止住 `PRD_INSTOCK` 当前报错。

缺点：

- 会话异常被当成数据的根因仍在。
- 其他表后续仍可能复现类似问题。

### 方案 B: 中等修复

在查询入口层、写库前校验层、生命周期层三处同时补强。

优点：

- 覆盖整条故障链。
- 修改点集中在现有模块内，改动边界清晰。
- 能同时解决当前报错和同类复发问题。

缺点：

- 变更面大于单点止血。
- 需要补齐对应测试。

### 方案 C: 重构式修复

将响应解析、脏数据治理、任务生命周期重构为统一状态机或管线。

优点：

- 长期结构最清晰。

缺点：

- 明显超出本次排障范围。
- 回归风险和交付周期不符合当前需求。

### 推荐方案

采用方案 B。该方案在成本、风险和收益之间最平衡，既能修复本次问题，又不会把任务扩大为重构工程。

## 6. 总体设计

修复分为三层，每层职责单一：

1. 查询入口层：只允许被明确识别为业务数据的记录进入后续数据流。
2. 数据整形与写库前校验层：对 `prd_instock` 的关键字段做严格校验，并在写库前再次兜底过滤。
3. 生命周期层：应用进入退出态后，禁止新任务提交，并安全切断 GUI 日志桥。

## 7. 详细设计

### 7.1 查询入口层

涉及模块：`src/core/kingdee_api.py`

#### 现状问题

- 当前响应解析允许多种宽松结构进入后续流程。
- 在某些返回形态下，异常对象可能被映射成“1 条数据”。
- “大页请求但只返回 1 条”的异常分页被过早判定为末页。

#### 设计变更

1. 增加统一响应判定逻辑，先判断“这是不是业务数据”，再做页数据计数与回调。
2. 对以下情况统一判定为查询失败：
   - `ResponseStatus.IsSuccess = false`
   - `Errors` 非空且不是业务数据容器
   - 返回结构明显属于错误包，而不是 `Result -> Result` 或 `Result -> Rows`
3. 仅当页数据被确认是业务数据后，才允许：
   - 计算 `got_count`
   - 调用 `page_callback`
   - 追加到 `all_rows`
4. 对“请求 `Limit=50000` 但返回 `1` 条”的情况，不再立即判定为末页。
   处理顺序改为：
   - 先检查是否为会话或错误响应
   - 如可判定为会话异常，则强制重登并重试当前页
   - 如无法恢复，则当前表单按查询失败处理

#### 预期结果

会话失效类错误对象不会再流入去重、写库、统计流程。

### 7.2 `prd_instock` 数据整形与写库前校验

涉及模块：`src/core/mysql_manager.py`、`src/core/upsert_engine_sqlserver.py`

#### 现状问题

- `_prepare_prd_instock_data()` 使用 `or 0` 兜底，掩盖空主键。
- `FBILLNO` 未按业务必填字段处理。
- staging 和普通批量写入前只过滤主键，不过滤 `FBILLNO`。

#### 设计变更

1. 在 `_prepare_prd_instock_data()` 中，对以下字段做严格校验：
   - `FID`
   - `FENTRYID`
   - `FBILLNO`
2. 任一字段缺失、为空字符串或仅空白字符时，该记录直接跳过。
3. 对跳过记录输出采样日志，日志口径明确为“无效记录跳过”，而不是“数据库写入失败”。
4. 去除 `or 0` 对空主键的掩盖行为，保留真实空值语义。
5. 在 SQL Server staging 路径下，对 `prd_instock` 增加二次兜底过滤：
   - 主键非空
   - `FBILLNO` 非空
6. 在普通批量写入路径下，对 `prd_instock` 同样应用等价过滤。
7. 过滤记录计入 `invalid`，不计入 `failed`。

#### 预期结果

即使上游仍漏进少量坏记录，`prd_instock` 也不会再因为 `FBILLNO` 为空触发整批回滚或整批失败。

### 7.3 生命周期与退出层

涉及模块：`src/core/data_sync.py`、`src/core/scheduler.py`、`src/utils/kingdee_sync_tool.py`、`src/gui/logging_utils.py`

#### 现状问题

- 程序进入退出流程后，同步框架仍可能继续排并发任务。
- 调度器停止与同步执行结束之间缺少关闭态约束。
- GUI 日志 handler 可能继续向已销毁对象发信号。

#### 设计变更

1. 在 `DataSyncManager` 中增加关闭态标记，例如“shutdown requested”。
2. 在开始新一轮并发表单同步前，检查关闭态：
   - 若已进入关闭态，则拒绝创建新的 `ThreadPoolExecutor` 任务。
   - 已在运行中的当前任务允许安全收尾。
3. 在 `cleanup_and_exit()` 中调整顺序：
   - 先设置关闭态
   - 再停止调度器
   - 再等待当前同步安全结束
   - 最后释放数据库和会话资源
4. 在 `AutoSyncScheduler` 中确保停止后不再进入新的 `_execute_sync()`。
5. 在 `GuiLogHandler.emit()` 中对已销毁或不可用的 signal emitter 做静默保护：
   - 不再抛出影响调度流程的异常
   - 该类异常只允许被吞掉或降为调试级别

#### 预期结果

应用退出后，不再出现：

- `cannot schedule new futures after interpreter shutdown`
- `Signal source has been deleted`

### 7.4 日志与统计口径

涉及模块：`src/core/form_sync_runner.py` 及相关日志统计逻辑

#### 现状问题

当前日志中“去重跳过”“无效记录跳过”“数据库写入失败”边界不清，容易造成成功率与告警信息不一致。

#### 设计变更

同步结果统一拆分为以下统计项：

- `fetched`: 被识别为业务数据的记录数
- `invalid`: 因字段缺失、结构异常而被主动跳过的记录数
- `inserted`: 实际插入或更新成功的记录数
- `failed`: 写库阶段真正失败的记录数

日志输出要求：

1. 去重必须单独记为“去重跳过”。
2. 字段缺失必须单独记为“无效记录跳过”。
3. 数据库异常必须单独记为“写库失败”。
4. 成功率计算不得与“仍有未插入记录”产生矛盾表述。

#### 预期结果

后续日志能直接区分问题位于接口层、数据质量层，还是数据库写入层。

## 8. 数据流变化

修复后的数据流如下：

1. 金蝶查询返回响应。
2. 查询层先判断响应是否为有效业务数据。
3. 若是会话异常：
   - 触发重登与页级重试
   - 仍失败则当前表同步失败并退出
4. 若是业务数据：
   - 进入页级回调或缓存
5. `prd_instock` 记录在数据准备阶段校验关键字段
6. staging / 普通写入前再次执行表级兜底过滤
7. 合法记录入库，无效记录进入 `invalid` 统计
8. 应用退出时先切换到关闭态，再阻断新任务提交

## 9. 错误处理策略

本次将相关异常分为三类：

### 9.1 会话/认证异常

特征：

- `ResponseStatus.IsSuccess = false`
- 错误信息包含“会话信息已丢失”“请重新登录”等

处理：

- 当前页不计入数据
- 强制重登并重试当前页
- 重试失败则当前表同步失败

### 9.2 数据质量异常

特征：

- 关键字段缺失，例如 `FBILLNO` 为空

处理：

- 单条记录跳过
- 记录采样日志
- 计入 `invalid`
- 不拖垮整批入库

### 9.3 生命周期异常

特征：

- 退出后仍提交并发任务
- 退出后仍向 Qt signal 发消息

处理：

- 进入关闭态后拒绝新任务
- GUI 信号发射失败静默处理

## 10. 测试策略

至少补以下验证：

### 10.1 查询解析测试

模拟以下返回：

- `ResponseStatus.IsSuccess = false`
- 错误包结构
- 异常单条列表

验证这些情况均不会进入正常数据流。

### 10.2 `prd_instock` 数据准备测试

验证以下场景：

- `FID` 缺失
- `FENTRYID` 缺失
- `FBILLNO` 缺失
- 合法记录

确认坏记录被跳过、合法记录仍可写入。

### 10.3 SQL Server staging 过滤测试

验证 `prd_instock` 混入坏记录时：

- 不再触发整批 `FBILLNO NULL` 失败
- 合法记录仍能继续完成 staging merge 或普通写入

### 10.4 退出竞态测试

模拟应用进入清理阶段后再触发调度，确认：

- 不再新建并发同步任务
- 不再报 `cannot schedule new futures after interpreter shutdown`
- 不再报 `Signal source has been deleted`

## 11. 验收标准

修复完成后，应满足：

1. `生产入库单` 不再因为单条坏记录导致整批写入为 0。
2. “会话已丢失”类错误对象不再混入业务记录。
3. 应用退出后不再出现新的并发同步启动日志。
4. 日志中不再出现 `cannot schedule new futures after interpreter shutdown`。
5. 日志中不再出现 `Signal source has been deleted`。
6. 同步统计可明确区分 `fetched / invalid / inserted / failed`。

## 12. 实施边界

本设计是实现前规格，不直接包含代码修改。后续实现计划需要围绕以下顺序展开：

1. 查询入口层修复
2. `prd_instock` 校验与写库兜底
3. 生命周期与退出保护
4. 日志与统计口径统一
5. 测试补齐与回归验证
