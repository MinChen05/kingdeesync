# 自动调度独立页面设计

日期：2026-04-21

## 背景

当前桌面工作台已经有“调度中心”页面，用于手动调度、运行矩阵和任务明细查看。项目中同时也存在一套自动调度能力和对应的 `SchedulePage`，但它没有作为正式导航页接入主壳层，信息架构上也没有和“调度中心”形成稳定分工。

结果是：

- 用户可以理解“调度中心”是在做手动调度，但找不到一个清晰的“自动调度”入口。
- 自动调度相关配置散落在不同页面，容易造成配置归属混乱。
- 手动调度和自动调度在视觉上缺少统一的工作区语言。

本设计的目标是补上一个独立的“自动调度”页面，并让它与“调度中心”保持一致的桌面工作台风格，同时对这两类页面的职责进行明确拆分。

## 目标

- 新增一个独立的“自动调度”导航入口，与“调度中心”并列出现。
- 自动调度页面与调度中心共享统一的工作区骨架和视觉风格。
- 自动调度页面只承载现有自动调度能力：
  - 启用开关
  - 执行间隔
  - 调度类型
  - 启动/停止
  - 当前状态、最近执行、下次执行
  - 实时日志
- 自动调度表单范围继续沿用“表单配置”页面维护的默认表单集。
- 梳理配置归属，避免手动调度和自动调度互相覆盖策略。

## 非目标

- 不在本次实现中增加 cron、工作日、每日固定时刻、多计划任务等高级调度规则。
- 不在自动调度页面里直接编辑具体表单列表。
- 不重做底层调度器状态模型，只在页面层对现有能力做更清晰的承载。
- 不把手动调度和自动调度重新合并成单页或 Tab。

## 已确认决策

- 自动调度页面使用独立左侧导航入口，与“调度中心”并列。
- 自动调度页面只做现有自动调度能力，不扩展为复杂规则系统。
- 自动调度表单范围继续去“表单配置”页面设置。
- 自动调度类型迁移到新的自动调度页面里设置。
- 采用共享“调度工作区骨架”的方案，使“调度中心”和“自动调度”统一视觉结构。
- 当 `SYNC.default_forms` 为空时，自动调度按“全部表单”理解，而不是阻止启动。

## 页面职责划分

### 调度中心

“调度中心”继续只承担手动调度相关工作：

- 手动发起同步任务
- 查看运行矩阵
- 查看任务详情抽屉
- 查看手动执行日志和运行态分布

该页面不再承担自动调度策略配置职责。

### 自动调度

“自动调度”页面只承担后台策略与运行职责：

- 是否启用自动调度
- 自动调度执行间隔
- 自动调度使用的同步类型
- 自动调度当前运行状态
- 最近执行时间、下次执行时间
- 自动调度日志
- 默认表单集摘要
- 前往“表单配置”和“调度中心”的快捷入口

### 表单配置

“表单配置”页面继续负责默认表单集，即 `SYNC.default_forms`。

自动调度页不直接编辑表单列表，只显示摘要并提供跳转入口。

### 同步页

“同步”页面继续保留手动同步 UI 偏好，但不应再承担自动调度策略的持久化职责。

## 配置归属

### 表单配置页拥有

- `SYNC.default_forms`

### 自动调度页拥有

- `SYNC.auto_sync`
- `SYNC.sync_interval`
- `SYNC.sync_type`

### 同步页拥有

- `SYNC.ui_manual_scope`
- `SYNC.ui_manual_form`
- `SYNC.ui_manual_mode`

### 设计约束

手动同步页面修改手动选择时，不应再隐式覆盖自动调度使用的 `sync_type` 或 `default_forms`。

## 共享骨架设计

新增一层共享的“调度工作区骨架”模块，用于承载“调度中心”和“自动调度”页面的共性布局与样式。该骨架只处理视觉和容器结构，不抽取业务逻辑。

### 骨架职责

- Hero 区承载
- Summary 卡片条承载
- 主工作区分栏布局
- 日志卡与日志工具条样式
- 主操作区布局
- 响应式重排逻辑

### 不放入骨架的内容

- 手动调度的过滤器、运行矩阵、抽屉
- 自动调度的策略表单、状态卡、表单摘要卡
- 实际调度器调用逻辑
- 手动同步执行逻辑

## 自动调度页面结构

自动调度页沿用共享骨架，但内容组织如下。

### Hero 区

- 标题：`自动调度`
- 眉标：`后台策略`
- 状态徽标：`未启用 / 已启用 / 运行中 / 已停止`
- 说明文案：突出“后台定时执行，无需手动触发”
- 主操作按钮：
  - `启动调度`
  - `停止调度`
  - `保存设置`
- 次操作按钮：
  - `前往表单配置`

### Summary 卡片条

- `自动调度`
- `执行间隔`
- `调度类型`
- `默认表单集`

### 主工作区

左侧为策略配置区，中间为运行状态与日志区，右侧为辅助与跳转区。

#### 左侧策略区

- 启用自动调度开关
- 执行间隔输入
- 调度类型选择器
- 默认表单集摘要
- 推荐值和操作提示

#### 中间运行区

- 当前状态卡
- 最近执行时间
- 下次执行时间
- 当前策略说明
- 自动调度日志

#### 右侧辅助区

- 前往表单配置
- 前往调度中心
- 说明“调度中心”和“自动调度”的职责区别

## 自动调度交互规则

### 保存

- 修改页面上的自动调度策略后进入“待保存”状态。
- 点击“保存设置”时，只保存策略配置，不自动启动调度器。

### 启动

- 点击“启动调度”时，先以当前页值为准保存配置，再启动调度器。
- 启动成功后刷新状态、最近执行时间、下次执行时间和日志。
- 启动动作会把 `SYNC.auto_sync` 置为 `True`。

### 停止

- 点击“停止调度”时，停止当前后台调度器。
- 停止动作不清空间隔和调度类型等策略值。
- 停止动作会把 `SYNC.auto_sync` 置为 `False`。

### 默认表单集为空

- 当 `SYNC.default_forms` 为空时，页面摘要显示为“全部表单（未单独限定）”。
- 启动调度时按“全部表单”处理。
- 页面仍给出说明提示，引导用户如需缩小范围可前往“表单配置”页维护默认表单集。

### 运行状态与启用状态

本次实现保持现有调度器语义：

- 启动调度意味着当前启用并运行
- 停止调度意味着当前停用并停止

不在本次实现中引入“已启用但未运行”的独立状态模型。

## 导航与壳层集成

主壳层导航调整为：

- `调度中心`
- `自动调度`

两者应位于同一组中，并在 `page_order`、`page_meta`、`pages` 注册链中完整接入。

顶部或其他遗留按钮如果仍使用旧的 `schedule` 页面跳转标识，需要统一迁移到新的页面 ID，例如 `auto_schedule`。

## 对现有页面的重构策略

### 调度中心页

`DispatchCenterPage` 保留业务逻辑，但其页面骨架、日志卡、响应式布局尽量改为复用共享调度工作区骨架。

### 现有 SchedulePage

不直接废弃现有 `SchedulePage`，而是将其演进为新的自动调度页面实现来源：

- 调整标题、文案和页面 ID
- 接入新的共享骨架
- 增加调度类型选择器
- 增加默认表单集摘要与跳转入口
- 保持现有调度器调用能力

如测试或导入链仍依赖旧名，可在本次提供兼容别名或渐进迁移。

### 同步页

需要修正手动同步页中“持久化自动调度策略”的行为边界，确保它只保存手动 UI 偏好，不再隐式改动自动调度配置。

## 数据流

### 自动调度页加载

1. 读取 `config_manager.get_sync_config()`
2. 提取 `auto_sync / sync_interval / sync_type / default_forms`
3. 将默认表单集格式化为摘要文本
4. 读取 `auto_scheduler` 运行态
5. 渲染 Hero、Summary、状态区和日志区

### 自动调度页保存

1. 收集界面上的开关、间隔、调度类型
2. 写回 `SYNC.auto_sync / SYNC.sync_interval / SYNC.sync_type`
3. 刷新本地原始值
4. 更新页面摘要与提示

### 自动调度启动

1. 保存当前策略
2. 读取默认表单集
3. 当默认表单集为空时，按全部表单处理
4. 调用调度器启动
5. 刷新页面运行态与日志

## 错误处理

- 保存失败时：
  - 保留用户当前界面输入
  - 显示错误反馈
  - 不修改当前运行态显示

- 启动失败时：
  - 显示失败原因
  - 保留当前策略设置
  - 不伪造“已运行”状态

- 停止失败时：
  - 显示失败原因
  - 保留当前显示的运行态，直到下一次状态刷新确认变化

- 默认表单集读取失败时：
  - 页面摘要显示为未知状态
  - 记录日志
  - 阻止启动并提示用户检查配置

- 主壳层存在“自动调度”独立导航入口
- 自动调度页可以实例化
- 自动调度页主操作按钮可见
- 自动调度页在窄屏下保持合理重排

### 配置归属测试

- 自动调度页保存时只影响：
  - `auto_sync`
  - `sync_interval`
  - `sync_type`
- 自动调度页保存时不影响 `default_forms`

### 手动同步回归测试

- 手动同步页修改 `ui_manual_mode` 时，不覆盖自动调度使用的 `sync_type`
- 手动同步页调整表单范围时，不覆盖 `default_forms`

### 启动路径测试

- 启动自动调度时使用当前自动调度页的策略值
- `default_forms` 为空时按全部表单处理
- 启动与停止后页面状态、摘要卡和日志同步更新

## 风险与控制

### 风险 1：配置串线

最主要的风险是手动同步和自动调度共用 `SYNC.sync_type` 带来的互相覆盖。

控制方式：

- 明确自动调度页是 `sync_type` 的唯一策略入口
- 手动同步页改为只保存手动 UI 偏好，不写自动调度策略字段

### 风险 2：导航接入不完整

当前主壳层存在旧的 `schedule` 跳转入口但页面未注册完整。

控制方式：

- 一并修正 `page_order`、`page_meta`、`pages`、按钮跳转目标
- 为新增 `auto_schedule` 页面补齐壳层测试

### 风险 3：共享骨架抽象过度

如果把过多业务逻辑抽到共享层，容易重新耦合手动调度和自动调度。

控制方式：

- 共享层只抽视觉结构和响应式容器
- 业务逻辑继续留在各自页面

## 实施边界

本次实现完成后，用户将获得：

- 一个独立的“自动调度”导航页
- 与“调度中心”风格一致的自动调度工作台
- 清晰的策略配置归属
- 清晰的手动/自动职责边界

本次实现完成后，用户仍不会获得：

- cron 风格高级规则
- 多计划任务
- 在自动调度页中直接编辑具体表单列表
