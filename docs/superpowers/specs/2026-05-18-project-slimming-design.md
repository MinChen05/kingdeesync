# 项目瘦身设计

## 1. 目标

本次瘦身的目标不是重写历史，也不是删除业务文件，而是先解决两个当前问题：

1. 仓库中长期跟踪了大量派生文件，导致工作区噪音高、提交容易夹带缓存和日志。
2. 本地目录存在明显空间占用，但当前项目约束不允许直接做破坏性删除，需要先给出可验证的清理证据。

本次实现只做最小改动，优先完成“止血”：

- 阻止缓存、日志、临时文件、本地配置继续进入版本控制。
- 提供一个本地清理 `dry-run` 脚本，列出可清理目录和预计释放空间，但不执行删除。

## 2. 当前证据与根因

当前项目代码体积并不大，`src/` 约为 `2.73 MB`。主要占用来自本地派生目录和历史跟踪内容：

- `.worktrees` 约 `4.6 GB`
- `.venv` 约 `741 MB`
- `.git` 约 `697 MB`
- `logs/` 约 `71 MB`

已跟踪的派生文件范围很大，包含：

- `__pycache__/`
- `.mypy_cache/`
- `.pytest_cache/`
- `.ruff_cache/`
- `.venv/`
- `.worktrees/`
- `logs/`
- `checkpoints/`
- `.idea/`
- `tmp-*.png`
- `.DS_Store`
- `config.local.ini`
- `config.ini.backup`

根因不是单一大文件，而是历史上把本地运行产物、IDE 文件、缓存和临时资源纳入了 Git 跟踪，导致：

- 当前工作区频繁出现无意义改动
- 日常提交容易夹带无关文件
- 仓库历史对象不断膨胀
- 本地空间也因为工作树和虚拟环境复制而持续增加

## 3. 约束

本次设计遵循以下边界：

- 不改数据库结构。
- 不删除业务源码、测试代码、文档和 SQL 脚本。
- 不重写 Git 历史。
- 不自动删除 `.worktrees`、`.venv`、`logs/` 等本地目录。
- 不提交密钥、密码或真实连接信息。

这意味着本次不会直接把 `.git` 历史体积降到最小，而是优先阻止继续变胖，并为后续手工清理提供明确清单。

## 4. 方案对比

### 方案 A：只补忽略规则

做法：

- 只修改 `.gitignore`

优点：

- 改动最小

缺点：

- 对已跟踪文件无效
- 当前仓库噪音不会消失
- 后续提交仍容易保留历史上已入库的派生文件

### 方案 B：仓库止血 + 本地 dry-run 清理

做法：

- 修改 `.gitignore`
- 对已跟踪的派生文件执行 `git rm --cached`
- 新增 `dry-run` 清理脚本

优点：

- 能真正停止跟踪当前已入库的派生文件
- 不删除本地文件，风险低
- 能给出本机可释放空间的清晰证据

缺点：

- `.git` 历史仍然保留旧对象

### 方案 C：重写 Git 历史

做法：

- 使用历史清理工具移除缓存、日志、虚拟环境和临时文件历史

优点：

- 仓库历史体积可以显著下降

缺点：

- 风险高
- 需要重写分支历史并协调协作者
- 不适合当前脏工作区直接执行

推荐采用方案 B。

## 5. 设计方案

### 5.1 仓库侧止血

修改 `.gitignore`，补齐当前遗漏项，并显式覆盖工作树内派生目录，至少包含：

- `.idea/`
- `.venv/`
- `.worktrees/`
- `config.ini.backup`
- `*.pyc`
- `**/__pycache__/`
- `**/.mypy_cache/`
- `**/.pytest_cache/`
- `**/.ruff_cache/`
- `**/.DS_Store`
- `**/logs/`
- `**/checkpoints/`
- `tmp-*.png`

随后对已跟踪的派生文件执行“停止跟踪但保留本地文件”的索引清理。预期效果：

- 这些文件从 Git 索引移除
- 本地目录仍保留，不影响当前运行
- 后续 `git status` 不再被缓存和日志刷屏

### 5.2 本地清理 dry-run 脚本

新增脚本 `scripts/dry_run_cleanup.py`，职责只有一个：输出清理建议，不执行删除。

脚本需要支持的候选路径至少包括：

- `.worktrees`
- `.venv`
- `logs`
- `.mypy_cache`
- `.pytest_cache`
- `.ruff_cache`
- `__pycache__`
- `checkpoints`
- `tmp-*.png`

脚本输出内容至少包括：

- 路径
- 类型（目录或文件）
- 当前大小
- 建议级别，例如“高收益 / 低风险”
- 说明，例如“重新创建成本高，请确认是否仍在使用”

脚本不接数据库参数，不读写业务数据，不改任何文件。

### 5.3 文档与使用说明

在 `README.md` 或相关文档中补充简短说明：

- 哪些目录是本地派生内容
- 如何运行 `dry-run` 清理脚本
- 为什么 `.worktrees` 和 `.venv` 不直接自动删除

说明要短，避免引入无关重构。

## 6. 实施边界

本次会清理 Git 跟踪状态，但不会做以下事情：

- 不清空 `logs/`
- 不删除 `.worktrees/` 下任何工作树
- 不删除 `.venv/`
- 不压缩或重建 Git 历史
- 不修改报表相关表结构

如果未来要继续瘦历史，应单独开一个高风险任务，先做分支协调和备份。

## 7. 验证方案

### 7.1 单元测试

如果新增脚本包含可测试函数，应补一个最小单元测试，至少覆盖：

- 目录大小统计
- 候选项枚举
- `dry-run` 输出不触发删除

### 7.2 脚本 dry-run

执行新增脚本，预期结果：

- 能看到 `.worktrees`、`.venv`、`logs` 等候选项
- 能看到预计释放空间
- 进程退出后本地文件仍然存在

### 7.3 Git 状态验证

执行索引清理后，预期结果：

- 派生文件显示为从索引删除
- `.gitignore` 能阻止这些文件再次被跟踪
- 后续生成新缓存后，`git status` 不再出现这些路径

## 8. 预期收益

完成后可得到以下收益：

- 仓库提交面更干净
- 代码审查噪音明显下降
- 本地清理有据可依
- 后续若要做历史瘦身，范围和风险已经被提前收敛

## 9. 不做的事

本次明确不做：

- Git 历史重写
- 自动物理删除文件
- 业务逻辑重构
- 数据库结构调整
- 性能优化类改造
