# 研发优化路线图设计

## 1. 目标

在保留现有 10 个方向和编号不变的前提下，把当前“并列罗列”的优化清单重排成研发可执行路线图，解决以下问题：

- 当前 10 条之间存在明显依赖关系，但原顺序没有展开。
- 部分方向在现有代码中已部分存在，不适合按“从零建设”理解。
- 性能、可靠性和字段适配问题混在一起，直接并行推进容易顺序错、验证难。
- 项目约束要求“改性能问题时先加日志或证据”，因此原顺序需要前移监控和证据项。

本次设计只输出路线图，不直接改代码。

## 2. 现状判断

结合当前仓库代码和文档，10 条中已有部分基础：

- `1 修复 FCANCELSTATUS NULL 问题`
  - 当前 `src/core/mysql_manager.py` 已存在 `FCANCELSTATUS` 相关字段处理线索。
- `2 字段截断自动适配`
  - 当前写库层已有 `_diagnose_string_truncation` 这类诊断能力。
- `4 分页并发控制`
  - 当前 `src/core/data_sync.py` 已有 `ThreadPoolExecutor` 与表级并发控制。
- `5 会话预热/保活增强`
  - 当前配置层已有 `keep_session_alive`，API 层已有会话失效相关测试。
- `7 断点续传覆盖更多失败场景`
  - 当前已存在 `CheckpointManager`，但恢复语义偏分页/行号。
- `8/9 监控项`
  - 当前已有 `metrics` 基础，但还不足以支撑失败归因和趋势管理。
- `10 大表单分批策略优化`
  - 当前已有 `batch_size`、`commit_every_n_batches` 和 staging 路径，但缺按表单策略。

结论是：这 10 条不是“全部从零开始”，而是“已有基础能力上的重排和补强”。

## 3. 设计原则

### 3.1 保留原编号

对外沟通仍保留原 10 条编号，避免和现有截图、汇报材料脱节。

### 3.2 研发执行按波次，而不是按原 A/B/C 平铺

原 A/B/C 分组更像汇报视角，不适合直接做研发排期。研发要按依赖关系拆成波次推进。

### 3.3 先证据、再止血、后提速

性能和可靠性优化如果没有证据链，后续所有“变快/变稳”的结论都无法验证。

### 3.4 优先补基础设施，避免继续散点补丁

字段适配、断点恢复、会话处理都应尽量进入统一抽象，而不是继续在单个 writer 或单张表里补特殊逻辑。

## 4. 推荐执行顺序

推荐顺序：

`8 → 9 → 1 → 6 → 3 → 2 → 7 → 5 → 4 → 10`

即分为三波：

- `P0 证据与止血`：`8, 9, 1, 6`
- `P1 字段适配与恢复`：`3, 2, 7`
- `P2 会话与吞吐优化`：`5, 4, 10`

## 5. 波次设计

### 5.1 P0 证据与止血

目标：

- 先回答“哪类失败最多、哪张表最差、是否在恶化”
- 优先消除明确已知失败源
- 阻止异常时的重试雪崩

包含条目：

- `8 写库失败明细日志`
- `9 增量同步成功率趋势面板`
- `1 修复 FCANCELSTATUS NULL 问题`
- `6 熔断机制`

为什么这样排：

- `8` 是 `9/1/6` 的观测前提。
- `9` 把 `8` 的明细沉成趋势指标。
- `1` 是单点止血项，应尽快清掉。
- `6` 依赖前面的失败分类，否则熔断策略无法精细化。

### 5.2 P1 字段适配与恢复

目标：

- 把零散字段兼容问题收敛成统一配置和统一策略
- 让失败恢复语义建立在“真实写入位点”上，而不是粗粒度分页状态上

包含条目：

- `3 全局字段映射配置文件`
- `2 字段截断自动适配`
- `7 断点续传覆盖更多失败场景`

为什么这样排：

- `3` 是字段适配的统一规则源。
- `2` 应建立在 `3` 的规则之上，而不是继续做“遇错再猜”。
- `7` 应建立在字段写入语义稳定之后，否则恢复点不可靠。

### 5.3 P2 会话与吞吐优化

目标：

- 在前两波把失败和恢复语义做稳后，再放大吞吐
- 避免“更快地失败”

包含条目：

- `5 会话预热/保活增强`
- `4 分页并发控制`
- `10 大表单分批策略优化`

为什么这样排：

- `5` 先处理长任务稳定性。
- `4` 再做按表级的动态并发控制。
- `10` 最后按大表特征做批次策略个性化。

## 6. 十个方向的研发化定义

### 6.1 `1 修复 FCANCELSTATUS NULL 问题`

**定位：** `P0` 单点止血

**改动模块：**

- `src/core/mysql_manager.py`
- 必要时补统一字段适配入口

**实施重点：**

- 在写入前对 `prd_mo` / 相关表的 `FCANCELSTATUS` 做显式空值转换
- 不允许继续依赖隐式类型/默认值兜底

**测试点：**

- 空值输入时写入成功
- 非空合法值不被误改

**验收条件：**

- `FCANCELSTATUS` 相关写库失败不再出现为主要失败源

**风险：**

- 默认值语义若未对齐业务，会变成“写入成功但业务含义错误”

### 6.2 `2 字段截断自动适配`

**定位：** `P1` 运行时兜底

**改动模块：**

- `src/core/mysql_manager.py`
- `src/core/upsert_engine_sqlserver.py`

**实施重点：**

- 不建议“盲目自动截断”
- 应改为“诊断字段 -> 按配置规则处理 -> 留痕”

**测试点：**

- 超长值能定位具体字段
- 命中规则后按预期处理
- 无规则时明确报错而非静默丢值

**验收条件：**

- 截断类错误不再整批拖垮

**风险：**

- 静默截断会损坏数据质量

### 6.3 `3 全局字段映射配置文件`

**定位：** `P1` 基础设施

**改动模块：**

- 建议新增 `src/config/field_mappings.json`
- `src/config/config_accessors.py`

**实施重点：**

- 统一定义字段重命名、默认值、空值策略、长度策略、类型转换
- 逐步把表级特殊逻辑从 writer 中收敛到配置

**测试点：**

- 至少选 `prd_mo`、`eng_bomchild`、`ap_payable` 三类差异表做回归

**验收条件：**

- 新增字段适配不再优先改 writer

**风险：**

- 若配置设计过度复杂，维护成本会高于收益

### 6.4 `4 分页并发控制`

**定位：** `P2` 吞吐控制

**改动模块：**

- `src/core/data_sync.py`

**实施重点：**

- 对超大分页表单按页数、失败率、表规模动态降并发
- 不是简单继续提高线程数

**测试点：**

- 超过 20 页的大表和小表分别回归
- 对比 timeout、总耗时、API 压力

**验收条件：**

- 大表 timeout 下降，小表吞吐不明显退化

**风险：**

- 全局降并发会误伤小表

### 6.5 `5 会话预热/保活增强`

**定位：** `P2` 稳定性增强

**改动模块：**

- `src/core/kingdee_api.py`
- 配置读取层

**实施重点：**

- 长任务启动前预热
- 跨午夜轮次前主动保活
- 会话异常与业务失败分流

**测试点：**

- 会话失效重试
- 跨日轮次保活逻辑

**验收条件：**

- 因会话丢失导致的整批失败明显下降

**风险：**

- 保活频率过高会变成无意义请求

### 6.6 `6 熔断机制`

**定位：** `P0` 止血

**改动模块：**

- `src/core/data_sync.py`
- `src/core/kingdee_api.py`
- 重试/调度层

**实施重点：**

- 按表单和失败类型熔断
- 连续异常后临时暂停，而不是无边界重试

**测试点：**

- timeout、session error、SQL error 至少三类连续失败场景

**验收条件：**

- 错误高峰时不再出现重试雪崩

**风险：**

- 熔断粒度过粗会拖停无关表单

### 6.7 `7 断点续传覆盖更多失败场景`

**定位：** `P1` 恢复语义

**改动模块：**

- `src/core/data_sync.py`
- `CheckpointManager` / `SyncCheckpoint`

**实施重点：**

- 从“按行号/分页状态”恢复，升级到“按已成功写入位点/批次/主键”恢复

**测试点：**

- 写库到一半失败后重跑
- 断点恢复不重复写、不从头扫全表

**验收条件：**

- 大表重试时间显著缩短

**风险：**

- 位点定义和写入语义不一致时会重复或漏写

### 6.8 `8 写库失败明细日志`

**定位：** `P0` 证据前置

**改动模块：**

- `src/core/form_sync_runner.py`
- `src/core/mysql_manager.py`
- `src/core/upsert_engine_sqlserver.py`
- 指标/审计出口

**实施重点：**

- 结构化输出失败记录
- 至少包含表单、目标表、记录标识、批次、失败类型、异常摘要

**测试点：**

- 字段截断、空值、唯一键、连接异常等典型失败分类

**验收条件：**

- 能定位“哪条失败、为什么失败”

**风险：**

- 明细日志量过大，需要控制采样或上限

### 6.9 `9 增量同步成功率趋势面板`

**定位：** `P0` 证据聚合

**改动模块：**

- 优先复用 `src/core/metrics.py`
- 必要时增加单独 metrics 落盘

**实施重点：**

- 把成功、失败、跳过、重试沉成表单级、天级指标

**测试点：**

- 同一表单多轮运行后趋势统计正确

**验收条件：**

- 能快速看到哪张表成功率在恶化

**风险：**

- 如落表，需要单独评审数据落盘位置和非报表表结构影响

### 6.10 `10 大表单分批策略优化`

**定位：** `P2` 最终提速

**改动模块：**

- SQL Server 写入层
- 表级配置层

**实施重点：**

- 从“全局统一 batch”改成“按表单策略”
- 优先覆盖 440 万级大表

**测试点：**

- 选超大表、中表、小表做三组回归

**验收条件：**

- 大表耗时下降，内存峰值和单批回滚成本可控

**风险：**

- batch 过大可能放大锁竞争和失败回滚代价

## 7. 研发排期建议

建议按批次而不是按单条平铺排期：

### 批次 1

- `8, 9, 1, 6`

目标：

- 先拿到失败证据和趋势
- 先止住已知失败源和重试雪崩

### 批次 2

- `3, 2, 7`

目标：

- 把字段适配和断点恢复抽成可复用能力

### 批次 3

- `5, 4, 10`

目标：

- 在稳定性和恢复语义稳定后再提吞吐

## 8. 统一门禁

每一批至少满足：

- 相关单元测试通过
- 相关脚本或模拟流程 dry-run
- 如涉及 SQL Server 写入，说明预期日志变化
- 用 `8/9` 产出的指标对比优化前后效果

## 9. 不建议的做法

本路线图明确不建议：

- 在没有失败明细和趋势证据前直接调并发/调 batch
- 把字符串截断做成无审计的静默自动截断
- 让断点恢复继续只基于粗粒度行号
- 把 `.worktrees`、会话失败、分页并发、字段适配混在一批里同时推进

## 10. 输出形式建议

如果要回写到原图或研发周会材料，建议保留原编号，但在每条后追加两个字段：

- `执行波次`
- `前置依赖`

这样既不破坏现有汇报材料，也能让研发直接排期。
